# Агрегатор новостей — лабораторные по базам данных

Проект содержит SQL для КТ-02 и локальный стенд PostgreSQL.
Схема создаётся, но исходные данные и сценарии имеют подтверждённые ошибки.
Бизнес-логика и оригинальные SQL-листинги пока не исправлены.
Исходные документы, отчёты и журналы хранятся только в `local/`, которая
исключена из Git. Подробный аудит на этой машине: `local/AUDIT_REPORT.md`.

## Запуск

Нужен Docker с Compose v2. Для извлечения и пересоздания проверок нужен Python 3
без дополнительных библиотек. PostgreSQL и psql устанавливать отдельно не нужно.

```sh
docker compose up -d --wait postgres
docker compose --profile audit run --rm checks
```

Первый запуск применяет обе исходные миграции в одной транзакции. Получаются
12 пустых таблиц. Ошибочный `sql/seed/report_test.sql` автоматически не загружается.
Проверки сами создают временные данные в отдельной схеме и откатывают её.

Успешный аудит выводит `AUDIT_PASS` и завершается с кодом 0. В нём
`known_issue | PASS` означает **воспроизведённый дефект**, а не исправление.
Неожиданный результат даёт `AUDIT_FAIL` и ненулевой код.

Параметры по умолчанию: сервер `127.0.0.1`, порт `55432`, база `news_aggregator`,
пользователь `news_app`, пароль `news_local_password`. Это локальные учебные значения.
При необходимости скопируйте `.env.example` в `.env` и измените настройки до
первого запуска. `.env` не входит в Git. Для уже созданного тома изменение
переменных не переименовывает базу и не меняет пароль автоматически.

Открыть SQL-консоль с параметрами текущего контейнера:

```sh
docker compose exec postgres sh -c 'exec psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"'
```

Например, можно выполнить `\dt` и `SELECT * FROM news;`. Основная база после
проверок останется пустой — рабочий согласованный seed предстоит подготовить
после обсуждения исправлений.

## Состав проекта

| Путь | Что содержит |
| --- | --- |
| `local/source/` | Локальная копия Word-отчёта и манифест извлечения; вне Git |
| `local/docs/source/` | Локальные Markdown-копии двух лабораторных и замечаний; вне Git |
| `migrations/` | Две исходные миграции, up и down |
| `sql/seed/report_test.sql` | Исходные данные вместе с исходными ошибочными INSERT |
| `sql/scenarios/` | Три исходных SQL-сценария жизненного цикла |
| `sql/negative/` | Шесть исходных негативных примеров |
| `compose.yaml`, `docker/00-init.sql` | Новый локальный запуск PostgreSQL и миграций |
| `tests/`, `run_checks.sql` | Новые автоматические проверки исходного состояния |
| `scripts/` | Извлечение, генерация проверок, сбор доказательств |
| `local/evidence/` | Локальные журналы выполнения SQL и результаты проверки; вне Git |
| `docs/schema.md` | Схема, отражающая текущий SQL, с фактическими кардинальностями |
| `local/AUDIT_REPORT.md` | Локальный подробный аудит и предложения; вне Git |

## Повторение аудита

```sh
python3 scripts/build_checks.py --check
docker compose --profile audit run --rm checks
python3 scripts/collect_evidence.py
```

Последняя команда сохраняет журналы в `local/evidence/`. Для стандартных параметров
она работает сразу. Если имя базы или пользователя изменено в `.env`, передайте
те же значения через переменные окружения `POSTGRES_DB` и `POSTGRES_USER`
при запуске Python. Этот скрипт не меняет данные в `public`.

Строгое выполнение исходного seed в доказательствах завершается с кодом 3 —
это ожидаемый результат аудита дефекта. Исполнение остальных листингов в
режиме продолжения после ошибки также даёт SQL-ошибки. Их код завершения 0
не означает, что весь SQL выполнился успешно; смотрите журналы и `execution.json`.

Скрипт извлечения привязан к позициям листингов в предоставленном DOCX.
Исходник не входит в Git. При наличии локальных материалов можно проверить
совпадение SQL с отчётом: `python3 scripts/extract_report.py --check`.
Для изменённого отчёта сначала обновите диапазоны `BLOCKS` и границы разделов
в `scripts/extract_report.py`, сверив их с новым документом. Затем:

```sh
python3 scripts/extract_report.py local/source/report.docx
python3 scripts/build_checks.py
```

Генератор проверок содержит ожидания именно для текущего исходника. При новых
миграциях или изменении сценариев их нужно пересмотреть, а не считать прежние
ожидания универсальными тестами готового приложения.

## Остановка и хранение

```sh
docker compose stop
docker compose start
```

Данные сохраняются в томе `bd-news-labs_pgdata`. При обычном повторном запуске
начальные миграции не выполняются повторно. Новые миграции нельзя применять
простым перезапуском контейнера: механизм учёта применённых версий пока не
реализован. Up/down-файлы из отчёта сохранены как исходные листинги.

Для удаления именно учебного стенда вместе с его данными:

```sh
docker compose down -v
```

Эта команда удаляет том проекта. Для обычной остановки используйте `stop`.

Выбран готовый официальный образ PostgreSQL 18 с закреплённым SHA-256.
Отдельный Dockerfile не нужен: своих расширений и приложения пока нет.
Том размещён в `/var/lib/postgresql`, как требует образ PostgreSQL 18.
Описание поведения образа: [официальная документация](https://hub.docker.com/_/postgres).
