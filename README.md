# Агрегатор новостей — лабораторные по базам данных

PostgreSQL 18, три версионируемые миграции, согласованные демонстрационные данные,
SQL-сценарии пользователя, источника и новости, негативные примеры и авточекеры.
Требования относятся к проектируемой системе; веб-приложение и настоящий сборщик
RSS/API в рамках КТ-01 и КТ-02 не реализуются. SQL-сценарии имитируют их события.

## Запуск базы

Нужен Docker с Compose v2. PostgreSQL и psql отдельно устанавливать не нужно.

```sh
docker compose up -d --wait postgres
```

На пустом томе миграции 001, 002 и 003 применяются в одной транзакции.
Создаются 12 пустых таблиц; демонстрационные данные загружаются отдельной командой.

| Параметр | По умолчанию |
| --- | --- |
| Сервер | `127.0.0.1` |
| Порт | `55432` |
| База | `news_aggregator` |
| Пользователь | `news_app` |
| Пароль | `news_local_password` |

Перед первым запуском можно скопировать `.env.example` в `.env` и изменить настройки.
`.env` исключён из Git. Изменение переменных для существующего тома не меняет
автоматически имя базы, пользователя или пароль.

Если том уже содержит схему после миграций 001 и 002, примените **один раз** 003:

```sh
docker compose exec -T postgres sh -c 'exec psql -X -v ON_ERROR_STOP=1 -1 -U "$POSTGRES_USER" -d "$POSTGRES_DB" -f /workspace/migrations/003_model_consistency.up.sql'
```

Миграция 003 требует, чтобы уже сохранённые новости имели непустые заголовок,
URL и текст/выжимку. Некорректные строки она не подменяет. Все миграции выполняются
однократно и по порядку; автоматического журнала применённых версий пока нет.
`down` выполняются в обратном порядке: 003 → 002 → 001.
Откат 001 удаляет таблицы вместе с данными.

## Демонстрационные данные и сценарии

После применения всех миграций на пустых таблицах:

```sh
docker compose exec -T postgres sh -c 'exec psql -X -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB" -f /workspace/run_demo.sql'
```

`run_demo.sql` загружает seed и выполняет три сценария в одной транзакции.
При ошибке изменения этой загрузки откатываются. Seed отказывается работать,
если любая из 12 таблиц уже содержит данные: повторный запуск не стирает и не
перезаписывает существующие записи.

Seed содержит 3 роли, 3 пользователя, 5 категорий, 5 источников, 5 новостей,
4 запуска, 6 результатов импорта и связанные записи. После сценариев получаются
4 пользователя, 6 источников и 6 новостей. Связи находят по уникальным email/URL
и `RETURNING`; фиксированные ID не используются.

Порядок для демонстрации отдельных файлов: seed → `01_user.sql` → `02_source.sql`
→ `03_news.sql`. Сценарии рассчитаны на один проход после загрузки seed; сценарий
новости можно повторить отдельно — сохранённый URL будет обработан как дубликат.
Для независимых повторных прогонов всего комплекта используйте авточекеры.

Открыть SQL-консоль:

```sh
docker compose exec postgres sh -c 'exec psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"'
```

Например, `SELECT id, source_id, status FROM scrape_run ORDER BY id;` показывает
историю запусков. Для выхода используйте `\q`.

## Автоматическая проверка

```sh
docker compose run --rm checks
```

Сервис `checks` запускает PostgreSQL при необходимости, ждёт готовности базы,
выполняет проверки и завершается. При обычном запуске базы он не стартует.
Успех — **37 сообщений PASS**, итог `passed_checks = 37` и код выхода 0:

- 22 проверки схемы и существенных ограничений;
- 3 проверки согласованности реального seed;
- 5 проверок жизненных циклов и сохранения связей при отключении категории;
- 7 проверок отказов из `sql/negative/`.

Сообщения `ERROR` во время последних семи негативных примеров ожидаемы: после
каждого примера проверяется SQLSTATE, изменения откатываются к savepoint.
Неправильный отказ или неожиданно принятая запись дают ненулевой код выхода.

Проверки создают отдельную схему с собственными таблицами и последовательностями,
применяют все миграции и выполняют реальные SQL-файлы проекта. В конце всё
откатывается. При аварии откат происходит при закрытии соединения. Таблицы,
данные и последовательности `public` не меняются; сервис не применяет к ней
новые миграции и не загружает в неё seed.

## Состав проекта

| Путь | Содержимое |
| --- | --- |
| `migrations/001_init.*.sql` | Создание/удаление исходных 12 таблиц |
| `migrations/002_add_scrape_run_status_check.*.sql` | Допустимые статусы запусков |
| `migrations/003_model_consistency.*.sql` | Отключение категорий и обязательная сохранённая копия |
| `sql/seed/report_test.sql` | Исправленный согласованный набор данных |
| `sql/scenarios/` | Три исправленных SQL-сценария жизненного цикла |
| `sql/negative/` | Семь примеров ожидаемых нарушений ограничений |
| `run_demo.sql` | Загрузка данных и сценариев в основную схему |
| `run_checks.sql`, `tests/` | Повторяемая проверка в отдельной схеме |
| `compose.yaml`, `docker/00-init.sql` | Запуск и первая инициализация PostgreSQL |
| `.env.example` | Пример настроек подключения |

При обычном отключении источника меняется его статус; при отключении категории —
`is_active`. Это сохраняет новости и подписки. Физическое удаление через `DELETE`
остаётся технической операцией с последствиями, заданными FK, включая CASCADE.

Авточекеры подтверждают SQL из этих лабораторных. Проверка пароля до хеширования,
авторизация, HTTP-запросы, канонизация URL и построение ленты относятся к будущему
приложению. Как минимум одна категория и совпадение источника новости с запуском
обеспечиваются импортом в одной транзакции и проверяются на демонстрационных
данных; отдельные FK сами по себе не запрещают любой произвольный SQL, который
нарушит эти бизнес-правила.

Отчёты, исходный Word, журналы и вспомогательные инструменты находятся в
игнорируемой папке `local/`. Исправленные Markdown-версии отчётов и пояснения
к изменениям хранятся в `local/reports/`; в Git они не добавляются.

## Остановка

```sh
docker compose stop
docker compose start
```

Данные сохраняются в томе `bd-news-labs_pgdata`. Для удаления стенда вместе с
данными используется `docker compose down -v`; для обычной остановки — `stop`.
