# Агрегатор новостей — лабораторные по базам данных

SQL из отчёта КТ-02 и локальный запуск PostgreSQL 18.
Схема создаётся с нуля. Исходные SQL-листинги сохранены без исправлений;
демонстрационные данные и сценарии содержат выявленные ошибки.

## Запуск

Нужен Docker с Compose v2. PostgreSQL и psql отдельно устанавливать не нужно.

```sh
docker compose up -d --wait postgres
```

При первом запуске на пустом томе применяются миграции 001 и 002 в одной
транзакции. Создаются 12 пустых таблиц. `sql/seed/report_test.sql`
автоматически не загружается, поскольку содержит ошибочные INSERT и статусы.

Параметры подключения по умолчанию:

| Параметр | Значение |
| --- | --- |
| Сервер | `127.0.0.1` |
| Порт | `55432` |
| База | `news_aggregator` |
| Пользователь | `news_app` |
| Пароль | `news_local_password` |

Для изменения настроек скопируйте `.env.example` в `.env` перед первым
запуском. `.env` исключён из Git. Для существующего тома изменение переменных
не переименовывает базу и не меняет пароль автоматически.

Открыть SQL-консоль с настройками текущего контейнера:

```sh
docker compose exec postgres sh -c 'exec psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"'
```

В консоли `\dt` показывает таблицы, а `SELECT * FROM news;` — сохранённые новости.

## Автоматическая проверка схемы и ограничений

```sh
docker compose run --rm checks
```

Сервис `checks` запускает PostgreSQL при необходимости, ждёт готовности базы
и выполняет `run_checks.sql`. При обычном запуске базы этот сервис не стартует.
Успех — 18 сообщений `PASS`, итог `passed_checks = 18` и код выхода 0.
Любое неожиданное принятие некорректных данных, нарушение проверки или ошибка
SQL дают ненулевой код выхода.

Проверки применяют обе миграции с нуля в отдельной схеме и используют собственные
согласованные данные с идентификаторами из `RETURNING`. Проверяются наличие
таблиц и ключей, допустимые вставки, дубликаты email и URL, составной ключ
избранного, обязательный заголовок, внешние ключи основных сущностей,
длина хеша, статусы и действия `RESTRICT`, `CASCADE`, `SET NULL` при удалении.
В конце транзакция откатывается: тестовая схема, данные и её последовательности
не сохраняются. При ошибке транзакция откатывается при завершении соединения.

Это проверка миграций и существующих ограничений. Она не проверяет, что схема
уже применена к `public`, и не подтверждает все бизнес-правила, которые пока
не реализованы в SQL. Исходные данные, сценарии и негативные примеры из отчёта
не входят в этот запуск; их ошибки остаются отдельными задачами.
`sql/scenarios/` предназначена для ручной демонстрации жизненных циклов трёх
сущностей после исправления данных и идентификаторов в сценариях.

## Состав репозитория

| Путь | Содержимое |
| --- | --- |
| `migrations/` | Две миграции из отчёта, up и down |
| `sql/seed/` | Исходный листинг демонстрационных данных |
| `sql/scenarios/` | Три SQL-сценария из отчёта: пользователь, источник, новость |
| `sql/negative/` | Шесть негативных примеров из отчёта |
| `compose.yaml` | Запуск PostgreSQL 18 и отдельного сервиса проверок |
| `docker/00-init.sql` | Применение миграций при первой инициализации |
| `run_checks.sql` | Запуск проверок в отдельной схеме с откатом |
| `tests/integrity.sql` | Необходимые проверки схемы и ограничений для КТ-02 |
| `.env.example` | Пример параметров подключения |

Отчёты, исходный Word-файл, журналы и вспомогательные инструменты хранятся
локально в `local/`, которая исключена из Git. Инструменты аудита находятся
в `local/debug/` и не нужны для запуска базы.

## Остановка и хранение данных

```sh
docker compose stop
docker compose start
```

Данные сохраняются в томе `bd-news-labs_pgdata`. При повторном запуске
начальные миграции не выполняются заново. Для последующих изменений схемы
нужен отдельный порядок применения новых миграций.

Для удаления учебного стенда вместе с его данными:

```sh
docker compose down -v
```

Для обычной остановки используйте `stop`.
