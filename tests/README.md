# Проверки исходного проекта

`checks.sql`, `run_checks.sql` и генератор `scripts/build_checks.py` созданы при аудите.
В DOCX были только названия `run_checks.sql` и `tests/checks.sql`, без листингов.
Они не выдаются за код команды из лабораторной.

Проверяются исходные миграции, данные, три написанных сценария и шесть
негативных примеров, а также связанные с ними уже заявленные бизнес-правила.
Невыполненные дополнительные задания и лабораторная 3 не реализуются.

Сначала повторяется каждый оператор исходного seed, включая ошибочные.
Ожидаемые ошибки ловятся отдельно, с точным SQLSTATE и именем ограничения.
Затем проверяются исходные сценарии с оставшимися данными. Из-за повреждённых
предусловий некоторые операторы проходят не так, как обещает отчёт.
После этого создаются отдельные предпосылки для проверки ограничений:
это новые тестовые записи, а не исправленный seed.

`kind=constraint` и `kind=schema` проверяют исправные части проекта.
`kind=source_replay` описывает фактическое исполнение оригинальных листингов.
`kind=known_issue` подтверждает существующий дефект или несогласованность.
PASS для known_issue означает, что дефект воспроизведён, а не устранён.
Если поведение изменится, проверка завершится с FAIL и ненулевым кодом.

Тестовая схема и созданные в ней последовательности находятся в одной
транзакции, которая откатывается. `public` не изменяется. Повторный запуск
проверен. Одновременные запуски используют одно имя схемы и могут ждать
друг друга; это локальный учебный стенд.

После редактирования оригинального отчёта обновите позиции листингов в
скрипте извлечения и пересоздайте извлечённые файлы,
затем при осознанном изменении ожидаемых результатов обновите генератор.

```sh
python3 scripts/extract_report.py --check
python3 scripts/build_checks.py --check
docker compose --profile audit run --rm checks
```
